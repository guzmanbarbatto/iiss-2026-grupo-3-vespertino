# Historias de Usuario Funcionales

Requerimientos del sistema descritos desde la perspectiva del usuario final para el desarrollo ágil. La columna **Estado** dice qué cubre el sistema al cierre de la Iteración 6; lo que falta está en el [roadmap](../arquitectura/roadmap.md).

| ID | Rol | Funcionalidad (Quiero...) | Beneficio (Para...) | Estado |
| :--- | :--- | :--- | :--- | :--- |
| **HU-1** | Usuario del Hogar | que el sistema encienda la calefacción automáticamente durante el horario más barato de UTE | despertar con la casa caliente sin pagar tarifas eléctricas excesivas. | **Parcial.** El controlador mantiene cada habitación en su temperatura y no enciende nada en la tarifa punta configurada en el sitio. No busca el horario más barato (tarifa valle) ni precalienta para una hora dada |
| **HU-2** | Dueño de Casa | poder simular el consumo eléctrico antes de encender múltiples habitaciones | asegurarme de que no superaré mi potencia máxima contratada y evitar cortes de luz. | **No implementada.** El controlador garantiza en todo momento no superar la potencia contratada, pero no ofrece una simulación previa |
| **HU-3** | Usuario del Hogar | preguntarle a un asistente virtual (GenAI) cómo optimizar mi consumo esta semana | recibir recomendaciones de uso personalizadas basadas en el pronóstico del clima. | **Parcial.** El servidor MCP permite que un agente de IA consulte el estado de la casa y el histórico de temperaturas, e inicie, detenga o accione switches. No hay datos de consumo ni pronóstico del clima |
| **HU-4** | Administrador del Sistema | contar con endpoints de la API para accionar switches, iniciar/detener el Controlador y validar la consistencia de las habitaciones | poder operar la calefacción de forma remota y garantizar que la configuración de las habitaciones no tenga errores ni IDs duplicados. | **Cumplida.** `POST /control/comandos` inicia y detiene el control, y `PUT /sitio` valida el inventario completo (campos, rangos e IDs duplicados). Accionar un switch a mano se hace con la tool `accionarSwitch` del MCP: el contrato del controlador no tiene ese endpoint, y cada switch tiene su propia API (§3 y §4 de `interop-v2`) |
| **HU-5** | Dueño de Casa | que todas las operaciones de la API requieran autenticación con una clave en el header `X-API-Key` | proteger el acceso al sistema para que solo aplicaciones o personas autorizadas puedan controlar la calefacción de mi hogar. | **Cumplida.** La historia pedía originalmente un token Bearer; se cambió a `X-API-Key` porque es lo que pide el contrato de la cátedra ([D03](../arquitectura/decisiones.md#d03-autenticación-con-x-api-key)) |
